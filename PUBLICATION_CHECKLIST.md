# Publication checklist

Complete the local checks first. The final section intentionally requires the future GitHub owner and is not performed by repository automation.

## Local repository

- [x] Add an OSI-compatible Apache-2.0 license.
- [x] Add contribution, conduct, security, architecture, privacy, and self-hosting guidance.
- [x] Keep `.env` files, runtime metadata, build output, and local logs untracked.
- [x] Replace the tracked personal Tailscale hostname with automatic detection and configuration variables.
- [x] Add reproducible install, CI, browser audit, and dependency update configuration.
- [x] Scan the original history with Gitleaks before rewriting it; no credential leaks were detected.
- [x] Replace the pre-publication history with a clean initial commit and keep a complete backup outside the repository.
- [x] Attribute the clean history to the maintainer's public GitHub identity using a GitHub noreply address.

## GitHub repository settings

- [ ] Create a private staging repository, add `origin`, and push the reviewed clean history.
- [ ] Change the repository visibility to public only after explicit maintainer review.
- [ ] Set a concise description, project topics, and a public homepage or demo when available.
- [ ] Enable Issues and private vulnerability reporting.
- [ ] Enable dependency graph, Dependabot alerts and security updates, secret scanning, and push protection.
- [ ] Protect `main` with required CI status checks and disabled force pushes.
- [ ] Review the Community Standards profile and fix every actionable warning.
- [ ] Confirm the repository owner's public profile and verified commit email identify the maintainer accurately.

## First release and Codex for OSS evidence

- [x] Add sanitized 2D, 3D, and mobile screenshots generated by the browser audit.
- [ ] Enable GitHub Pages and run the manual deployment workflow after the repository becomes public.
- [ ] Tag and publish the first release with release notes from `CHANGELOG.md`.
- [ ] Triage real issues, review pull requests, and maintain a visible release cadence.
- [ ] Record honest adoption signals such as stars, forks, active installations, external contributors, and references.
- [ ] Prepare the OpenAI organization ID and a concrete API-credit plan for issue triage, pull request review, testing, security review, and release maintenance.
